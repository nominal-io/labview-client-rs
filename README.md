# nominal-labview

A LabVIEW client for [Nominal](https://nominal.io), built on top of
[`nominal`](https://docs.rs/nominal) — Nominal's canonical Rust SDK.

## Why this exists

- **Match the rest of Nominal's APIs.** The Python, TypeScript, and Rust
  clients all speak to the same platform through officially maintained SDKs.
  This project gives LabVIEW users the same footing, backed by the same
  canonical Rust SDK — not a hand-rolled reimplementation of the HTTP API.
- **Reliability and maintainability.** All business logic — request building,
  JSON parsing, auth, retries — lives in the `nominal` crate and is owned by
  Nominal's API team. This repo contains only a thin, highly readable
  translation layer. When the platform's API changes, the Rust SDK changes,
  and a scheduled CI job here catches the drift as a failed build — not as a
  runtime surprise on a test rig.
- **Minimal dependencies, fast builds.** The FFI crate has four runtime
  dependencies (`nominal`, `tokio`, `chrono`, `once_cell`). No codegen
  frameworks, no binding generators in the dependency tree. A clean build is
  quick, and there is very little surface area to break.

## How it works

The design is three layers, each deliberately dumb:

```
┌────────────────────────────────────────────────────────────┐
│  LabVIEW wrapper VIs            lv_src/                    │
│  Friendly, idiomatic LabVIEW API: error clusters, string   │
│  buffers handled for you, handles wired through.           │
│  Maintained by hand in LabVIEW.                            │
├────────────────────────────────────────────────────────────┤
│  Auto-generated VIs             lv_src/client/VIs/         │
│  One VI per exported C function, generated by LabVIEW's    │
│  Import Shared Library wizard from the header + DLL.       │
│  Never edited by hand — regenerated when the DLL changes.  │
├────────────────────────────────────────────────────────────┤
│  C-ABI FFI layer (this repo's Rust code)   crates/ffi/     │
│  Flat `extern "C"` functions that only use types the       │
│  import wizard can parse: i32/u32/f64, C strings, i32      │
│  handles. Zero business logic — each function converts     │
│  arguments, calls one `nominal` method, converts the       │
│  result.                                                   │
├────────────────────────────────────────────────────────────┤
│  `nominal` crate (Nominal's official Rust SDK)             │
│  Owns everything real: HTTP, auth, JSON, domain types.     │
└────────────────────────────────────────────────────────────┘
```

**Downward (Rust side):** the FFI layer wraps the Rust SDK and exposes *only*
what LabVIEW's code generator can accept. That constraint is strict — no
structs, no 64-bit integers, no callbacks, no returned arrays. Anything that
doesn't fit is flattened: objects become `i32` handles into a registry,
strings use caller-supplied buffers, lists become count-plus-index getters,
timestamps cross as `f64` Unix milliseconds. Every function returns an `i32`
error code and nothing else, so the wizard can wire every return value into
LabVIEW's error cluster in one pass.

**Header generation:** the `cbindgen` CLI turns the Rust source into a single
C header (`lv_src/bin/nominal_ffi.h`). That header plus the built DLL/SO is
everything the Import Shared Library wizard needs — it generates the ~270 raw
VIs with no manual signature patching.

**Upward (LabVIEW side):** above the raw generated VIs sits a hand-maintained
wrapper layer that turns the C-flavored calling convention back into idiomatic
LabVIEW — allocating string buffers, converting error codes to error clusters,
converting timestamps — so the end user never touches a raw buffer or a
needed-bytes out-param.

## Repository layout

| Path | What it is |
|---|---|
| `crates/ffi/` | The Rust FFI crate — one source file per resource type (asset, run, dataset, ingest, …), mirroring the `nominal` crate's layout |
| `lv_src/bin/` | Built shared libraries (`nominalClient_64.dll`, `_32.dll`, `_64.so`) + the generated header |
| `lv_src/client/` | The LabVIEW library: wizard-generated VIs plus wrapper subVIs |
| `lv_src/tests/` | LabVIEW-side test VIs exercising full resource lifecycles |
| `justfile` | All build entry points — nobody runs raw `cargo` commands |
| `CLAUDE.md` | The full design document: type-conversion rules, error handling, naming conventions, testing strategy |

## Building

Requires Rust, [`just`](https://github.com/casey/just), and the `cbindgen`
CLI (`cargo install cbindgen` — deliberately a CLI tool, never a dependency).

```bash
just build-win64    # Windows x64 → lv_src/bin/nominalClient_64.dll
just build-win32    # Windows x86 → lv_src/bin/nominalClient_32.dll
just build-linux    # Linux x64  → lv_src/bin/nominalClient_64.so
just test           # marshaling + mocked-HTTP tests, no network needed
```

CI rebuilds all targets on every push, and a scheduled workflow bumps the
`nominal` dependency daily and runs the test suite — that failing loudly is
the early-warning system this project exists to provide.

Regenerating the LabVIEW VIs from a new DLL/header is a deliberate manual
step (Tools → Import → Shared Library in LabVIEW), done by the maintainer.

## Design rules

The detailed conventions — why no 64-bit integers ever cross the boundary,
how string buffers work, how staging handles replace string arrays, the
handle-registry design — live in [CLAUDE.md](CLAUDE.md). Read that before
adding or changing any exported function.
